# 知乎 URL → 游戏 · 模拟管线演示

状态：已真实跑通一次完整闭环（2026-09-12）。给知乎官方的参考方向演示。

## 这是什么

回答一个问题：**如果官方开放"按 URL 取内容"的接口，游戏能变成什么样。**

当前官方开放平台没有"输入一个知乎链接、返回他人全文"的接口（各内容接口只给摘要，唯一全文接口仅限本人创作，详见 [vip-flow.md](vip-flow.md)）。因此这条管线把"URL 取内容"环节**模拟**出来，其余环节全部真实：

| 环节 | 真实/模拟 | 说明 |
|---|---|---|
| 内容来源 | 真实 | 比赛接口的 20 篇授权试读段（每篇约 3000 字），已缓存到 `content/zhihu-library/` |
| URL 解析 | 模拟 | `zhihu.com/market/paid_column/.../section/<id>` → 内容标识。实测比赛接口 `work_id` 与站内 section 编号一致，未来官方若开放接口可直接替换这一环节 |
| 剧情分析 | **真实** | 知乎直答 `zhida-fast-1p5` 调用，输出人物/主线/转折点/开放线索的 JSON |
| 剧情生成 | **真实** | 知乎直答基于分析结果生成游戏故事包（结构化 JSON） |
| 人工审读 | 真实 | 修正了 5 处舞台指示残留、规范化节点 id，然后才编译 |
| 编译与游玩 | 真实 | 走既有 `compile --reviewed` 管线，7 节点 / 2 结局，浏览器实际游玩至终幕 |

## 一次真实运行的记录

内容：《穿越大明，我被崇祯偷听心声》（凉风有信，2630 字试读段）。

```
npx tsx scripts/zhihu-demo.ts library                      # 拉取 20 篇到本地库
npx tsx scripts/zhihu-demo.ts import --id 1654134122145320960
npx tsx scripts/zhihu-demo.ts generate --id 1654134122145320960 --model zhida-fast-1p5
# 人工审读 content/demo-candidate.json（见下节"审读修正"）
npx tsx scripts/story-cli.ts compile --input content/demo-candidate.json \
  --source content/demo-source.json --reviewed --output public/story-package.json
npx vite build && npx vite preview                         # 127.0.0.1:4175 游玩验证
```

浏览器实测：入梦 → 客栈借枕 → 选择"入梦赴京" → 殿上心声 → 折戟之令 → 选择"当殿苦谏" → 终幕·殿上的雪 → 结局《原典人生》收藏入人生册。全程无报错。

生成质量要点（直答一次生成 + 人工小幅修订）：

- 原文人物的转译到位：周鉴（装糊涂的穿越者）→ 卢生，崇祯 → 权相，孙传庭出关危机 → 裴行舟船队被强令出港，"心声被听见"的核心设定完整保留。
- 六角色语气有区分（审读时的判断）：权相威急、裴行舟"船可以借，信用借不来"、江映禾"水不认谁的名声，只认堤上的每一道缝"，各角色台词盲认得出。
- 两条路线各有真实代价：official 线赌"被看见"的风险，travel 线赌"留下来"的承担；终幕以人物命运收束，不是数值结算。

## 人工审读做了什么（不是无脑发布）

直答输出质量高但不是零缺陷，审读修正了三类问题：

1. **5 处舞台指示混入对白**：`（心声）`、`（按剑）`、`（对白，因路线而异）`这类括号指示被改为旁白或删除——演出动作由引擎负责，台词只留台词。
2. **一处台词丢失**：心声改旁白后补了一拍卢生的实际台词（"必败……四万精锐……"）。
3. **id 规范化**：直答用下划线（`n2_official`），校验器只认 `^[a-z][a-z0-9-]*$`，逐个改连字符。

这也回答了一个设计问题：**AI 生成不能免掉审读**。边界恰好也是好处——审读负担很轻（15 分钟内完成三处修正），远低于从零写作。

## 调用直答的四条实测结论

踩过的坑，写给后续接入者：

1. **system 角色被忽略**。直答收到 system 消息会回自我介绍。全部指令必须并入单条 user 消息。
2. **单次大生成会 504**。"3000 字输入 + 完整故事包输出"一次请求超时（fast 和 thinking 档都超）。解法是两步：先分析（短输出）、再创作（输入用分析结果，不带原文）。
3. **内容安全层按故事而异**。《山回路转不见鸡》（含性暗示桥段）即使只做分析也会触发兜底回复；《穿越大明》《吃人心的小妖怪》全部正常。选材时留意。
4. **额度与档位**：实测直答 100 次/天（VIP 账号）、知乎搜索 5000 次/天。一次完整生成消耗 2 次直答额度。

## 与未来官方接口的对接点

如果官方将来开放"按 URL 取内容"，替换的只有 `runImport` 里从本地库读取的那一行——`parseZhihuUrl` 已支持 `paid_column/section`、`answer`、`zhuanlan/p` 三种链接格式，`importExcerpt` 的完整性标注体系也已就位。分析、生成、审读、编译全链路不用动。

这也正是这个演示想说的：**缺的只是一个"按 URL 取授权内容"的官方接口，其余部分游戏侧已经准备好了。**

## 诚实边界

- 试读段 ≠ 全文。来源标注如实写明"以比赛接口授权试读（约 2630 字）为全部原文依据，非全文"。
- 超出试读段的剧情标记 `origin: original`（衍生创作），试读段内的标记 `adapted` 并给段落引用。
- demo 包是真实 API 调用产物（`content/demo-raw-answer.txt` 保存直答原回复），不是事后手写冒充。
- 当前 `public/story-package.json` 是演示包，**不是发布状态**。恢复内置《枕中记》包：`npx tsx scripts/story-cli.ts compile --output public/story-package.json`（不带 `--input` 即导出内置包），然后重新 `npx vite build`。
- 生成消耗了真实额度（直答 2 次 + 若干次调试调用）。
