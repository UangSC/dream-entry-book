# 入梦书产品说明与实施计划

## 产品定位

入梦书是一款面向知乎故事读者与创作者的互动阅读产品。我们希望把用户在阅读盐选、短篇小说与社区故事时产生的“如果是我，我会怎么选”，变成可以亲历的一段叙事体验。

产品以知乎内容为发现入口，以获得授权的故事为创作基础，通过 Agent 辅助梳理人物、事件和分歧，将文字组织为可游玩的入梦书。读者进入故事，在关键时刻作出选择，看见人物的反应和选择的回响，并能回到知乎继续阅读、发现作者和参与讨论。

入梦书的核心是可复用的故事体验载体。当前示例用于验证这种载体能否承载长篇分支、情绪演出与完整阅读流程；产品长期价值来自更多作品被发现、制作、体验和讨论。

## 创作思路与用户需求

知乎故事擅长用人物处境、生活细节与悬念引发共鸣。读者会为一个决定遗憾，也会在评论中争论人物是否还有别的路。单纯阅读全文之后，这种参与感往往只能停留在想象中。

我们希望给它一个新的表达入口：让读者暂时站到角色的位置上，在故事允许的范围内作出选择。选择既包括推动情节的大分歧，也包括能表达人物关系的细微态度。后续叙事记住这些选择，让用户感到自己参与过这段经历。

首批目标用户包括喜欢盐选与短篇故事、希望获得更强代入感的读者；希望尝试互动改编、但不具备游戏开发能力的内容创作者；以及愿意围绕同一篇作品交流不同选择的社区用户。

## 核心体验

### 从知乎发现下一场梦

用户在现有书架弹窗里浏览知乎黑客松官方故事目录，查看标题、作者与正文开头；也可以通过知乎搜索寻找原作、题材和相关讨论。搜索保留原始链接和溯源参数，明确将结果作为摘要展示，全文阅读回到知乎。

普通盐选链接首先是原作入口和来源标识，不被视为任意付费全文的下载凭证。可用于制作的正文来自活动提供内容、创作者授权或用户有权使用的材料。

### 让 Agent 辅助理解故事

用户选择故事片段后，可建立真实知乎直答分析任务。报告梳理人物动机、核心冲突、至多三个值得选择的时刻，以及氛围与声音建议。任务在后台运行，用户可以收起窗口继续阅读，再从头像菜单查看结果。

报告区分原文事实与改编建议。当前真实接入已经覆盖线索分析；后续将逐步串联分支编排、人物与道具一致性检查、演出资源配置、图验证和人工审读，形成完整制作流程。

### 进入可参与的故事

入梦后，界面向画面边缘收拢，标题逐渐消散，立绘与对白框结合，场景和音乐随叙事推进。选择按钮的形态和动作呼应角色心境，犹豫、逞强或害羞都可以通过轻微的交互被感知。

这些演出服务于阅读节奏。用户可以手动翻页，也可以开启自动播放；在需要选择时，自动播放会停下。减少动态效果、字体与声音设置为不同阅读习惯保留空间。

### 让选择留下回响

故事用条件旗标记住已经发生的行动，后续对白与结局回应这些行动。用户可以回望已走过的分歧，比较不同道路；完成后将结局收入梦册。书架支持多本入梦书，每本独立保存阅读进度，并支持标准包导入、导出和离线体验。

### 带着体验回到知乎

原作署名与来源贯穿书架、作品说明和终幕。阅读完成后，用户可以回到知乎查看原作与作者，或搜索同一人物处境下的讨论。首页守梦人也会适时邀请用户到知乎寻找下一本入梦书。

后续计划提供可由用户主动分享的选择回响卡，围绕“我为什么这样选”组织交流，让互动体验转化为更有内容的社区讨论。

## 适配知乎社区的价值

**为故事内容增加体验入口。** 一篇作品既可以被读，也可以被短暂地经历。入梦书希望吸引偏好视觉叙事与互动体验的用户接近知乎故事，再通过原作入口形成继续阅读的兴趣。

**让讨论更贴近人物处境。** 当读者亲自承担过一次选择，讨论就有机会从简单评价角色，转向理解信息差、关系和后果。不同路线为同一作品提供具体、可比较的话题。

**降低创作者尝试互动表达的门槛。** 标准化书包和 Agent 辅助分析让创作者可以集中在人物、分歧与作品气质上，而不必为每篇故事重新开发一套游戏。创作者对可改编范围和最终叙事保有审核位置。

**让来源回流形成连续体验。** 内容发现、作者署名、原文链接与知乎讨论在产品中有明确位置。我们希望将“知乎发现故事—入梦体验—回知乎阅读和交流—发现下一篇作品”连成用户自然愿意走完的流程。

这些是产品希望验证的价值方向，当前没有虚构用户增长、阅读转化或商业收入数据。

## 技术方案

前端使用 Vite、React 和 TypeScript，将故事数据、确定性叙事引擎与演出层分开。节点、选择、旗标、条件拍和结局构成可验证的图；背景、音乐、表情和交互动作通过演出配置连接到叙事。相同输入与存档可以确定性回放，便于检查分支可达性和定位问题。

入梦书以 .dreambook 包分发剧情与媒体。导入时校验结构、文件和哈希，书包不执行任意脚本；IndexedDB 与本地存档承担书架和当前设备的阅读状态，Service Worker 提供静态素材离线缓存。账号 API 与授权回调不进入缓存。

后端使用 FastAPI 与 SQLite，提供账号、最近七天的游玩足迹、异步任务和入架记录。Authorization Code 流程已具备本地模拟实现和真实知乎适配位置；正式登录仍需赛事分配的 App ID、App Key，以及平台确认的用户资料和回调协议。Access Secret 只在服务端使用，与 OAuth 应用凭据分开管理。

官方调用由后端统一转发至固定端点。目录和详情使用缓存，相同请求合并；知乎搜索按提交触发，不逐字请求；直答按用户建立的任务调用，结果可回看。服务中断后不会自动重复真实直答请求。项目还有独立的每日预算，便于控制同一账号下共享的开放平台额度。

## 知乎开放能力与当前进展

| 能力 | 在产品中的用途 | 当前状态 |
| --- | --- | --- |
| 黑客松官方故事目录与详情 | 发现可体验内容，保留作者与内容来源 | 已接入真实接口；属于本次活动能力 |
| 知乎搜索 | 寻找原作、题材和讨论，返回知乎阅读 | 已接入真实 Access Secret 鉴权 |
| 知乎直答 | 人物、冲突和入梦分歧线索分析 | 已接入真实异步分析任务 |
| 知乎 Authorization Code | 统一用户身份和账号手记 | 模拟链路可用，正式平台登录待配置联调 |
| Agent 自动制作完整游戏 | 将授权小说编排、审读和装订为书包 | 完整制作目前为流程演示，逐步建设 |

我们选择与故事体验直接相关的能力。热榜、全网搜索、知识库等暂不为展示接口数量而接入，后续以用户场景和可验证价值决定是否扩展。

## 原型验证

当前已经实现多书书架、存档与分歧回望、情绪演出、自动播放、结局回响、离线阅读、账号手记，以及官方内容发现和线索分析入口。原型使用一篇三线故事验证长篇分支承载：七份终幕文本可达，192 条路径经过确定性回放，三条主线路和终幕组合已完成桌面操作验收。

这项验证证明的是叙事引擎和呈现系统可以支撑完整体验，并不意味着任意输入小说都已经能够一键生成同等质量的游戏。原型当前以桌面端为主，移动端将在统一适配阶段推进。

## 后续实施计划

第一阶段完成公网可访问作品、正式知乎登录联调及更多官方故事样例，让评审和用户可以稳定完成发现、分析与体验流程。

第二阶段完善创作者制作台：允许编辑和确认角色关系、章节骨架与分歧范围，再由 Agent 编排；通过结构验证、条件回放和人工审读控制人物失真与支线冲突。以少量高质量作品验证制作流程，再扩大内容规模。

第三阶段增加移动端体验、可分享的选择回响和创作者作品页，逐步打通用户主动分享与知乎原作讨论的衔接。

效果评估将关注官方内容卡片到原作的点击、首次入梦完成率、章节和终幕完成率、分歧重玩率、分析报告到制作的转化，以及每本书的接口调用成本。所有指标均为后续验证计划，不作为已有成绩陈述。
