# 入梦书：知乎故事的 AI 互动叙事平台

## 一、项目概述

入梦书面向喜欢知乎故事、盐选内容和互动阅读的用户，也服务希望尝试互动改编的创作者。平台以知乎优质故事为内容入口，借助 AI Agent 将获得授权的故事整理为人物、事件、分歧和场景，再装订为可以亲自参与的互动叙事作品。

用户不只是阅读故事，也会在关键时刻站到人物的位置上作出选择。每一次选择都会被记录，并在后续情节、人物关系和结局中留下回响。读者可以重走不同路线、比较不同结局，并回到知乎阅读原作、了解作者和参与讨论。

“入梦书”是可持续扩展的故事载体：一本书包含剧情结构、互动规则、视觉素材、声音配置和阅读存档，可以在不同设备中导入、导出和继续阅读。

## 二、用户需求与产品机会

知乎故事擅长通过人物处境、生活细节和悬念引发共鸣。读者常常会思考“如果是我，我会怎么选”，但这种参与感通常停留在想象或评论区。入梦书把这种想象变成可亲历的叙事过程，让读者承担选择、观察后果，并形成属于自己的故事版本。

平台重点服务三类用户：

- 喜欢故事和沉浸式体验、希望增强代入感的读者；
- 希望把文字作品改编成互动内容、但缺少游戏开发能力的创作者；
- 愿意围绕人物选择、不同路线和结局展开交流的社区用户。

## 三、核心产品体验

### 1. 从知乎发现故事

用户可以浏览知乎黑客松故事与知识内容，也可以通过知乎搜索寻找原作、作者、题材和相关讨论。内容卡片保留标题、作者、摘要和原始链接；原作阅读回到知乎完成，确保来源清晰、作者署名完整。

对于可用于改编的内容，平台依据活动提供、作者授权或用户拥有使用权的正文进行制作，并在作品说明中展示来源与改编信息。

### 2. AI Agent 理解与编排

用户选择故事后，AI Agent 将正文整理为结构化创作资料，包括人物关系、时间线、地点、关键事件、叙事冲突和可互动节点。创作者可以查看、修改和确认这些资料，再决定故事的改编范围、风格和分支方向。

制作流程由多个职责清晰的 Agent 协同完成：故事解析、叙事设计、场景规划、视觉生成、声音设计和作品校验。每个 Agent 输出结构化中间结果，便于追踪来源、检查一致性和人工审阅。

### 3. 千人千面的入梦体验

同一篇原作可以生成不同的互动版本。生成时综合考虑用户选择的叙事偏好、改编尺度、关注的人物关系以及游玩过程中已经作出的决定，形成具有差异的分支、对白和结局。

这种差异不是简单改变措辞，而是让选择真正影响人物态度、事件顺序、信息揭示和最终代价。每个生成版本都保存输入资料、生成参数和版本标识，保证作品可以稳定读档、复盘和重玩。

### 4. 沉浸式互动阅读

入梦书以视觉小说式界面呈现故事：立绘、对白、背景、音乐和交互动作随叙事推进。用户可以手动阅读或开启自动播放；遇到关键选择时自动暂停。字体、动效和声音均可调节，以适应不同阅读习惯。

故事引擎使用条件旗记录玩家行动，使后续对白、人物关系和结局能够回应前面的选择。用户可以查看已走过的路线，重新体验其他分支，并把喜欢的结局收入梦册。

### 5. 从体验回到知乎

原作、作者和来源信息贯穿书架、作品详情与终幕。完成故事后，用户可以阅读原作、查看作者主页、搜索相关问题和讨论，也可以生成“我为什么这样选”的选择回响卡，主动分享自己的路线与结局，让更多小伙伴能够参与进来~！

平台希望形成“在知乎发现故事—进入入梦体验—比较不同选择—回到知乎阅读与交流—发现下一场梦”的连续路径。

## 四、知乎开放能力结合

| 知乎能力 | 产品用途 |
| --- | --- |
| 黑客松故事与知识内容 | 提供适合展示和改编的故事素材，保留作者与内容来源 |
| 知乎搜索 | 发现原作、作者、同题材内容和社区讨论 |
| 知乎直答 | 辅助提炼人物动机、冲突、分歧和创作方向 |
| OAuth 登录 | 让用户使用知乎账号登录，并在授权范围内管理个人内容 |
| 用户内容、关注与收藏 | 帮助用户从自己的知乎内容中发现适合改编的故事 |
| 知乎热榜 | 发现当下热门议题，为书架和创作提供灵感 |
| 知识库检索 | 支持长篇故事的人物问答、时间线核对和原文依据检索 |

所有知乎接口由服务端统一调用，按照授权范围、接口额度和缓存策略进行控制。作品展示保留真实来源，不把摘要冒充全文，也不替用户自动发布内容。

## 五、AI 制作与内容安全

平台将原文资料、创作指令、模型输出和最终作品分层保存。AI 先生成结构化剧情，再通过分支可达性、条件冲突、人物一致性和素材引用检查，最后进入创作者审阅。

作品保留原作者、来源地址、改编说明和素材使用依据。涉及完整正文的制作建立在活动提供、明确授权或用户有权使用的材料之上。URL 作为来源入口；正文解析使用可用的官方接口或用户主动提供的授权文本。

平台不让模型直接执行页面中的指令，不允许生成结果绕过来源标识、授权范围或安全校验。无法确认来源或权限的内容进入人工确认流程。

## 六、技术方案

前端采用 React、TypeScript 和 Vite，负责书架、阅读器、创作台和作品导入导出。故事数据、确定性叙事引擎与演出层分离，便于验证剧情并跨设备保存。

后端采用 FastAPI 与 SQLite，负责账号、OAuth 会话、故事导入、异步制作任务、作品版本和阅读记录。真实制作任务以服务端 Job 管理，支持状态查询、事件推送、取消、失败重试和幂等提交。

入梦书以 `.dreambook` 标准包分发，包含 `book.json`、剧情图、媒体资源、来源信息、版本号和校验哈希。导入时验证结构、文件和哈希；书包不执行任意脚本。IndexedDB 保存本地书架和阅读进度，静态素材支持离线缓存，账号凭据和 OAuth 回调不进入缓存。

## 七、实施路线

### 第一阶段：作品与登录基础

完成公网可访问的入梦书体验、知乎 OAuth 登录、官方故事内容接入和多本书架，形成从知乎发现、登录、阅读到回流的完整路径。

### 第二阶段：AI 创作台

打通正文导入、故事解析、人物与时间线编辑、分支编排、文字剧情生成和结构校验。创作者可以确认 AI 结果，再生成不同风格和不同偏好的互动版本。

### 第三阶段：视听制作与知识问答

接入背景、立绘、音乐和音效生成，建立素材版本与版权记录；使用知识库检索支持角色问答、原文依据展示和长篇故事的一致性检查。

### 第四阶段：社区传播与移动端

推出选择回响卡、作品页、作者页、路线比较和移动端适配，连接知乎原作、作者和讨论，让用户能够分享自己的入梦版本并发现更多作品。

## 八、项目价值与评估方式

入梦书为知乎故事增加互动体验入口，为读者提供更强的代入感，为创作者降低互动改编门槛，也让围绕人物和选择的讨论拥有更具体的共同经历。

项目将关注故事发现到原作阅读的点击率、首次入梦完成率、分支重玩率、结局分享率、分析到制作的转化率、创作者审阅通过率和单本作品的生成成本，并依据数据持续优化内容质量和用户路径。
