## 可保留的工程经验

- **路径与 URL 分开**：中文文件路径用本机路径 API；Web URL 用 URL API 和编码后的路由。旧的拼接错误不证明中文路径本身不可用。
- **转换需要验证**：六个官方 GIF 可尝试动画 WebP，保留透明、帧序与时长。旧记录的约 1.4MB 是过去产物数据，当前尚无加工副本。
- **音量需要听测**：旧记录终幕曲偏小，可保留“曲间响度一致”的教训；不要将过去的 RMS 值当跨曲风的标准。
- **"整理"不等于"精简"**：上一轮把 9 条音效收敛成 4 条发布成品，理解错了目标。用户要的是在体积可控前提下建立**更丰富的声音池**，不是减少素材数量。原件从未被删除（14 个一直在 source 层），但发布层只留 4 条、把其余记为"落选"，实际上丢掉了不同强度／质感／场景的变化。教训：涉及素材取舍时，先确认目标是"少而精"还是"多而有序"，别默认前者。同样地，"同一文件里有三下敲击"这类发现在收敛思路下是限制，在池化思路下是三个变体的来源。
- **来稿"可用"不等于"达标"**：用户确认 5 首 BGM"都可以用"指的是选曲合适，不代表技术规格合格。实测全部比 −20 LUFS-I 响 7.5–12 LU、真峰值都在 0 dBTP 以上（`bgm_1` 有 40,156 个满刻度采样）。选曲判断与规格判断要分开问、分开记。
- **裁切窗口要看包络，不能只看"有效内容窗"**：`轻触确认_文件_#1` 的静音检测给出有效窗 0–0.28 秒，但逐 5ms 包络显示里面有 0.035s、0.150s、0.205s 三下敲击。按有效窗裁会得到连响三下的确认音。`翻页声#3` 同理，真正的瞬态在 0.400–0.440 秒而非开头，裁尾会丢掉它。
- **生成需要档案**：保留原始回复、分析、源文本哈希、修改与审读，排除凭证。审读不能只替换 ID 和舞台指示，还要验证人物知识和分支因果。
- **版本需要保护**：构建变化保留旧存档，不能静默清空或不经核验迁移；恢复不能重复结算和一次性音效。
- **离线需要首次缓存**：静态包随服务器部署不等于从未访问过的离线设备已拥有它。离线就绪必须检查真实资源。

## 本轮音频加工中实际踩到的工具坑

以下四条是 2026-09-12 加工音频时真实发生并已修复的错误，全部可复现，记录以免重犯。

| 现象 | 原因 | 正确做法 |
|---|---|---|
| 裁切后的 `page.wav` 整段静音（−91 dB），另三条正常 | `-ss` 放在 `-i` 之后时，滤镜图看到的仍是原始时间戳（首帧 PTS=0.380s），`afade=t=out:st=0.332` 在首帧到达前就已走完，于是全程增益为 0。另三条 `ss=0` 才侥幸没触发 | 用 `atrim=start=..:end=..,asetpts=N/SR/TB` 先重置时间戳再挂 `afade`；或确认 seek 与滤镜的时间基一致 |
| `bgm-end.mp3` 的 LRA 从母版 17.2 LU 变成 11.3 LU，动态被压掉 | `loudnorm` 的 `linear=true` 在"实测 LRA > 目标 LRA"时会**静默回退到 Dynamic 模式**并做动态压缩，日志里只有一行 `Normalization Type: Dynamic`。我传了 `LRA=11` 而该曲实测 17.2 | 把 `LRA` 目标设到实测值之上（此处用 20）强制 Linear，或显式接受动态模式。每次都要检查报告里的 `Normalization Type`，不能假设 `linear=true` 就一定线性 |
| `volumedetect`、`loudnorm`、`astats` 报告为空 | 这些滤镜的报告打在 **info** 级，`-v error` 会一并吞掉 | 用 `-hide_banner -nostats` 保留 info 级；`ffprobe` 也不会替你打印这些滤镜结果 |
| 早期测速得到 147.6 BPM 且自相关峰仅 0.0002 量级（等于无峰） | 用 11.025kHz + 纯 RMS 包络测一段 LRA 只有 1.7 LU 的柔和脉冲，包络法灵敏度不足 | 改用分频带谱通量（1024 点 FFT、减滑动均值）+ 梳状自相关，峰值升到 0.711。倍速歧义靠分频带解决：宽带峰 143.6 BPM、中频带峰 72.0 BPM，说明基本拍是 72，宽带峰来自八分音符层 |

本轮扫描新素材时又踩到两个**测量方法**的坑，没有污染文档（所有已写入的数值都来自 `astats`/`volumedetect`/`loudnorm`，不是自建脚本），但必须记下来：

| 现象 | 原因 | 正确做法 |
|---|---|---|
| 同一文件自建脚本测出 −3.88 dB，`astats` 测出 −6.89 dB，差 3.01 dB | `ffmpeg -ac 1 -f f32le` 的立体声降混按 **(L+R)/√2** 归一（等功率），而 `-f s16le`/`-f s32le` 与 `astats` 按 **(L+R)/2** 归一。两者相差恰好 3.01 dB | 测电平别用 `-f f32le` 管道自己算。用 `astats`/`volumedetect`；必须自己算时统一走 s16/s32，或显式用 `pan` 指定降混系数 |
| 从 ffmpeg 输出的 WAV 管道读到 −1.93 dB，比源文件还响 | 假定 WAV 数据区从第 44 字节开始。ffmpeg 写了 `LIST/INFO` 块，实际 `data` 载荷从第 78 字节起，于是把头部字节当采样读了 | 永远搜索 `data` 块位置再取 `+8` 偏移，不要硬编码 44。或者直接用 `-f s16le` 裸流，没有头 |

这两条都属于"工具默认行为与直觉不符"，与前面四条一样，凡是自建测量脚本得出的结论，都要用 ffmpeg 官方滤镜交叉验证一次再写进文档。

另有两条不算错误但值得记的判断：`ffmpeg` 裸命令在本机 Bash 环境不在 PATH，须用 `/c/Program Files/ffmpeg/bin/ffmpeg.exe` 全路径；控制台以 GBK 渲染 stdout，中文显示为乱码属于终端表现，文件本身经校验是无 BOM 的合法 UTF-8，不要据控制台乱码去"修"文件编码。
